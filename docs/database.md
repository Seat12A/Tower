# Base de données

PostgreSQL 16 (Railway). SQLAlchemy 2 en asynchrone (asyncpg), migrations Alembic.

## Conventions

- Clés primaires `BIGINT GENERATED BY DEFAULT AS IDENTITY` ; identifiant public
  `UUID` séparé (`public_id`) quand la ressource est exposée.
- **IDs X et Discord en `BIGINT`** dans la base, **toujours sérialisés en chaînes**
  dans l'API et les événements (JavaScript perd la précision au-delà de 2^53).
- Statuts en `TEXT` avec contrainte `CHECK` générée depuis les enums du domaine
  (pas d'enum PostgreSQL, pénibles à faire évoluer).
- Horodatages `TIMESTAMPTZ`, valeurs par défaut `now()` côté serveur.
- Noms de contraintes et d'index déterministes (`NAMING_CONVENTION` dans
  `core/db/base.py`) : les migrations restent stables.
- Verrouillage optimiste sur `dossiers.version`, verrou de ligne
  (`SELECT … FOR UPDATE`) pour les transitions.

## Tables du socle

| Table | Rôle |
|---|---|
| `dossiers` | Dossiers de fact-check ou de modération (`kind`), statut, post X, assignation, lien de publication, version |
| `dossier_events` | Audit immuable : une ligne par transition (de, vers, acteur, motif, données) |
| `events` | Outbox transactionnelle (topic, agrégat, payload, acteur, `xid` de la transaction) |
| `event_cursors` | Position de chaque consommateur nommé dans l'outbox |
| `jobs` | File de travaux (file, type, payload, priorité, statut, tentatives, bail, dédoublonnage) |
| `service_clients` | Clients machine : nom, empreinte SHA-256 du token, scopes, révocation |
| `staff_members` | Équipe : ID Discord, rôles, actif |
| `error_reports` | Erreurs stockées, agrégées par empreinte (voir [error-handling.md](error-handling.md)) |

Tables à venir (voir [roadmap.md](roadmap.md)) : `observed_posts`, `observations`,
`watched_accounts`, `post_snapshots`, affirmations, groupes, verdicts, sources,
citations, profils de traitement, journal de coûts.

## Index notables

- `jobs` : index partiel `(queue, priority DESC, run_at, id) WHERE status = 'queued'`
  pour la réservation ; index partiel unique sur `dedupe_key` parmi les jobs actifs.
- `events` : `(xid, id)` pour la lecture sans trou.
- `error_reports` : index partiel sur les erreurs ouvertes.

## Migrations

```bash
uv run alembic revision --autogenerate -m "description"   # puis relire le fichier
```

```bash
uv run tower migrate            # upgrade head
```

```bash
uv run tower migrate --downgrade -1
```

- Les migrations vivent dans `src/tower/migrations/versions/`, nommées
  `AAAAMMJJ_<rev>_<slug>.py`, et sont livrées dans l'image.
- En production, `tower migrate` est le `preDeployCommand` du service gate : il
  s'exécute **avant** le nouveau déploiement, pendant que l'ancien code tourne encore.
- **Règle expand/contract** : chaque migration doit être compatible avec le code
  précédent.
  1. *Expand* : ajouter colonnes et tables (nullable ou avec défaut) et déployer le
     code qui écrit les deux formes.
  2. *Contract* : supprimer l'ancien dans un déploiement ultérieur.
  Jamais de renommage ni de suppression en une seule étape.
- Index sur une grosse table : `op.create_index(..., postgresql_concurrently=True)`
  dans une migration avec `autocommit_block()`.
- La CI vérifie que les modèles et les migrations concordent (`alembic check`).
